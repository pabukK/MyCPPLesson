# 第 44 课:算法选型与避坑

## 1. 拿到问题的四步

**第 1 步:弄清输入规模。**

这是最重要的一步,它直接决定什么算法够用。参考第 25 课的表:

| 规模 | 能接受的复杂度 |
| --- | --- |
| n ≤ 20 | `O(2ⁿ)`、`O(n!)` 都行 → 可以回溯、状态压缩 |
| n ≤ 5000 | `O(n²)` |
| n ≤ 10⁶ | `O(n log n)`、`O(n)` |
| n ≥ 10⁷ | 只能 `O(n)` 或更好,还要注意内存和常数 |

**第 2 步:明确要什么。**

- 只要一个数字(个数、最大值、最短距离)?→ 多半能 DP 或贪心,不用枚举。
- 要列出所有方案?→ 回溯(第 39 课)。
- 要判断可行不可行?→ 搜索或图算法。
- 要反复查询?→ 建索引(哈希表、树、前缀和、排序 + 二分)。

**第 3 步:看数据有什么特点。** 这一条常常直接给出答案:

| 特点 | 能用的招 |
| --- | --- |
| 数据已排序 | 二分、双指针 |
| 数据范围小(0 到 100) | 计数排序、直接开数组当下标 |
| 要求"连续的一段" | 滑动窗口、前缀和 |
| 只要前 k 个 | 堆、`nth_element` |
| 有依赖关系、先后顺序 | 拓扑排序 |
| 判断"是否同一组" | 并查集 |
| 求最优,且能拆成子问题 | 动态规划 |
| 网格、迷宫 | BFS(最短步数)、DFS(连通性) |
| 前缀匹配、自动补全 | 前缀树 |
| 缓存、淘汰 | LRU(哈希表 + 双向链表) |

**第 4 步:先写对的,再写快的。**

先写一个能跑的暴力版本(哪怕 `O(n²)`),用它当"标准答案",然后:

1. 确认暴力版在**小数据**上是对的。
2. 写优化版。
3. 两个版本对拍(第 23、40 课)。

跳过第 1 步,你会分不清"优化版错了"还是"暴力版本来就错了"。我在写这门课时犯过好几次后一种错:第 29 课的 `lower_bound`、第 30 课的窗口和、第 40 课的糖果、第 43 课的累乘,都是我手推错了,实测才发现。**手推会错,所以要对拍。**

## 2. 数据结构总表

| 需求 | 选择 | 查找 | 插入/删除 | 备注 |
| --- | --- | --- | --- | --- |
| 按下标访问,末尾增删 | `vector` | `O(n)` 遍历 | 末尾 `O(1)` | **默认选它** |
| 两头增删 | `deque` | `O(n)` | `O(1)` | 也能按下标访问 |
| 已知位置频繁增删,不要下标 | `list` | `O(n)` | `O(1)` | 很少用 |
| 按键查值,不要顺序 | `unordered_map` | 平均 `O(1)` | 平均 `O(1)` | 最坏 `O(n)` |
| 按键查值,要顺序、范围查询 | `map` | `O(log n)` | `O(log n)` | 自平衡树 |
| 去重、判断存在 | `unordered_set` / `set` | 同上 | 同上 | |
| 只取极值 | `priority_queue` | 极值 `O(1)` | `O(log n)` | 不能遍历成有序 |
| 后进先出 | `stack` | 顶 `O(1)` | `O(1)` | |
| 先进先出 | `queue` | 头 `O(1)` | `O(1)` | |
| 前缀查询、自动补全 | 前缀树 | `O(词长)` | `O(词长)` | 费内存 |
| 判断同组、动态合并 | 并查集 | 接近 `O(1)` | 接近 `O(1)` | |
| 字符串大量切片传参 | `string_view` | — | — | 不复制,但不能比原串久 |

## 3. 整门课的坑,集中复盘

按主题分类。每一条都在前面的课里出现过,这里当索引。

**内存(第 8 到 13 课)**

| 坑 | 后果 | 怎么办 |
| --- | --- | --- |
| `new` 了不 `delete` | 内存泄漏,长期运行的程序会挂 | 用 `vector`、`string`、`unique_ptr` |
| `delete` 两次 | 崩溃 | `delete` 后立刻 `= nullptr` |
| `delete` 后继续用 | 读到旧数据或乱码,时好时坏 | 同上 |
| 数组、vector 越界 | 悄悄改坏旁边的数据 | 用 `.at()`,注意下标 0 到 n-1 |
| 返回局部变量的引用或指针 | 悬空 | 别这么做 |
| 用 `new[]` 却用 `delete` 归还 | 未定义行为 | `new[]` 配 `delete[]` |
| 递归、链表、DFS 太深 | 栈溢出崩溃 | 改成循环或显式栈 |
| `unique_ptr` 链表不写析构 | 10 万节点销毁时崩 | 自己写循环释放的析构函数 |

**标准库(第 18、19、31、43 课)**

| 坑 | 后果 | 怎么办 |
| --- | --- | --- |
| `map`/`unordered_map` 用方括号读不存在的键 | 悄悄新增一项 | 只查不改用 `find` 或 `count` |
| `unique` 之后不 `erase` | 元素没少,尾部是垃圾 | `v.erase(last, v.end())` |
| `unique` 之前不排序 | 只去掉相邻重复,等于没做 | 先 `sort` |
| `accumulate` 用 `0` 起步求大数和 | 溢出成负数 | 写 `0LL` |
| 对未排序的数据用二分 | 不报错,结果错 | 先排序,或用哈希表 |
| 给 `sort` 的比较函数写 `<=` | 可能崩溃 | 必须严格 `<` |
| vector 增删后用旧迭代器 | 未定义行为 | 重新取 |
| 遍历哈希表时往里插入 | 迭代器失效 | 先记下来,遍历完再改 |
| 依赖 `unordered_map` 的遍历顺序 | 换编译器结果就变 | 需要顺序就排序,或用 `map` |
| `std::stoi` 不接异常 | 非法输入直接崩 | `try/catch` |

**算法实现(第 26 到 41 课)**

| 坑 | 后果 | 怎么办 |
| --- | --- | --- |
| 二分取中点写 `(l+r)/2` | 大数相加溢出 | 写 `l + (r-l)/2` |
| 二分的区间写法混用 | 死循环或差一 | 统一用左闭右开 |
| 非递归 DFS 出栈时不检查已访问 | 同一个点处理多次 | 出栈时 `if (visited) continue` |
| BFS 出队时才标记已访问 | 队列膨胀,慢 | **入队时**就标记 |
| 0-1 背包一维内层从小到大 | 同一件物品被选两次 | 从大到小 |
| 回溯忘了撤销选择 | 后面分支带着脏状态 | 做选择和撤销成对写 |
| 回溯去重写成 `i > 0` | 误杀合法解 | 写 `i > start`,且先排序 |
| 快速排序基准总选端点 | 有序数据退化 `O(n²)` | 选中间、随机或三数取中 |
| 归并、LCS 的下标错位 | 差一错误 | 打印小表对照手推 |
| KMP、Rabin-Karp 不复核哈希 | 冲突时结果错 | 哈希相等还要逐字符比 |
| 判断 DP 状态时漏维度 | 答案错 | 状态必须能唯一确定后续选择 |

**通用(第 23、25、40 课)**

| 坑 | 怎么办 |
| --- | --- |
| 凭"感觉有道理"就认定贪心正确 | 交换论证 + 和暴力法对拍 |
| 手推小数据当预期值 | 用标准库或暴力版当标准答案 |
| 只测正常输入 | 边界:空、1 个、最小最大、全相同 |
| 不估算复杂度就动手 | 先看 n 有多大 |
| 大 O 相同就以为速度相同 | 常数、内存访问模式差别很大(第 31、37 课实测) |

## 4. 完整案例:从暴力到可用

**问题:** 一个日志文件,每行是"用户ID 接口名 耗时毫秒"。要回答:**哪个接口的平均耗时最高?输出前 10 个。**

假设日志有 1000 万行,接口名约 500 个。

**第 1 步:估算。** 1000 万行,必须 `O(n)` 或 `O(n log n)` 扫一遍。`O(n²)` 完全不可能。

**第 2 步:暴力版(为了有个标准答案)。** 每来一行,就把整个文件重扫一遍统计这个接口 —— 显然 `O(n²)`,跑不完。但它给了我们一个"绝对正确"的参照。

**第 3 步:选数据结构。** 需求是"按接口名累计",这是典型的按键聚合 → 哈希表(第 31 课)。

每行一条记录:`用户ID 接口名 耗时毫秒`。比如:

```text
u1001 getUsers 120
u1002 getUsers 80
u1003 getOrders 300
```

<!-- stdin: u1001 getUsers 120\nu1002 getUsers 80\nu1003 getOrders 300\n -->
```cpp
// file: log_aggregate.cpp
#include <algorithm>
#include <iostream>
#include <string>
#include <unordered_map>
#include <utility>
#include <vector>

int main() {
    std::unordered_map<std::string, std::pair<long long, long long>> stats;

    std::string user_id, api;
    long long cost = 0;
    while (std::cin >> user_id >> api >> cost) {
        stats[api].first += cost;
        stats[api].second += 1;
    }

    std::vector<std::pair<std::string, double>> avgs;
    for (const auto& p : stats) {
        avgs.push_back({p.first, (double)p.second.first / p.second.second});
    }

    int k = std::min((int)avgs.size(), 10);
    std::partial_sort(avgs.begin(), avgs.begin() + k, avgs.end(),
                      [](const auto& a, const auto& b) {
                          if (a.second != b.second) return a.second > b.second;
                          return a.first < b.first;
                      });

    for (int i = 0; i < k; i++) {
        std::cout << i + 1 << ". " << avgs[i].first << " " << avgs[i].second << std::endl;
    }
    return 0;
}
```

(`user_id` 只是用来对齐日志格式,统计时用不上,读进来丢掉就行。`stats[api].first` 是总耗时,`.second` 是次数。`std::pair` 装两个值,第 32 课。)

上面那几行日志喂进去,输出是:

```text
1. getOrders 300
2. getUsers 100
```

**三个设计决定:**

1. **用 `unordered_map` 而不是 `map`。** 聚合阶段不需要顺序,要的是平均 `O(1)`。500 个接口差别不大,但接口名有几十万时差别就明显了(第 31 课实测约 2 倍)。
2. **用 `partial_sort` 而不是 `sort`。** 只要前 10 个,`O(m log 10)` 而不是 `O(m log m)`。m 是接口数,这里差别不大,但思路是对的:不做多余的工作(第 34、43 课)。
3. **比较函数里加"名字升序"作为第二关键字。** 平均耗时相同时,输出顺序就确定了,不会随哈希表的遍历顺序抖动(第 31 课:不要依赖 `unordered_map` 的顺序)。

**第 4 步:对拍。** 用暴力版(每个接口各扫一遍文件)在小数据上比对结果,确认一致(第 23、40 课)。

**第 5 步:实测。** 我生成了一个 1000 万行的日志(500 个不同接口名),跑了两个版本:

| 版本 | 耗时 |
| --- | --- |
| 排序 + 顺序扫描(把 1000 万行全部排序) | 3882 毫秒 |
| 哈希表聚合 + `partial_sort` | 210 毫秒 |

(我的机器,`-O2`。你的数字会不同。)

哈希表版快约 **18 倍**,比我预期的多得多。原因:

- 排序版要移动 1000 万个元素,每个元素含一个 `std::string`(32 字节)加一个整数,总共约 400 MB 的数据在内存里搬动,`O(n log n)` 次比较也大多是字符串比较。
- 哈希版只做 1000 万次哈希查找,累加到 **500 个**桶里。最后排序的对象只有 500 个,不是 1000 万个。

两个版本的前 10 名结果**完全一致**,这也是对拍(第 23、40 课)。

这个例子说明:**"减少要排序的数据量"往往比"换更快的排序算法"有用得多。** 聚合把 1000 万条压成 500 条,后面的任何操作都便宜了。这又一次印证:大 O 相同或相近时,常数和内存访问量才是决定性的(第 31、37 课)。

**这个案例的完整思路,就是第 1 节那四步:估规模 → 明确要什么 → 看数据特点 → 先写对的再写快的,最后对拍和实测。**

## 5. A*:导航软件背后的思路

第 36 课的 Dijkstra 有一个"浪费":它像水波一样**四面八方**扩散,而你要的只是到一个特定终点的路。

**A\* 的想法:** 给每个点加一个**启发式估计** `h(x)` = "从 x 到终点还要走多远"的估计值,然后优先扩展 `g(x) + h(x)` 最小的点。`g(x)` 是起点到 x 的实际距离。

```text
起点 S,终点 E,中间点 X

Dijkstra:比较 g(X) = S 到 X 已走的距离
A*:      比较 g(X) + h(X) = 已走的 + 估计还要走的

有了一条"往终点方向"的指引,不再四处扩散
```

**关键条件:`h` 不能高估真实距离**(叫"可采纳的")。在地图上,用**直线距离**当 `h` 就很合适:实际路程不可能比直线短,所以绝不会高估。这样 A* 的结果和 Dijkstra **一样正确**,但扩展的点数少得多。

```text
S 在左下,E 在右上。

Dijkstra 扩散:一个以 S 为中心的圆
A* 扩散:      一个沿 S->E 方向的椭圆

城市路网里,A* 通常能少扩展几倍的点
```

**用途:** 地图导航、游戏寻路(网格上的 A* 是标配)、拼图类问题的求解。

**代价:** 需要一个合适的启发函数。如果没有(或 `h` 恒为 0),A* 就退回 Dijkstra。如果 `h` 高估了,结果可能不是最短,但速度更快——这种"牺牲正确性换速度"的做法叫加权 A*,在实时性要求高的场合会用。

实现上和 Dijkstra 几乎一样,只改一行:堆里排的不是 `dist[node]`,而是 `dist[node] + h(node)`。

## 6. 学完之后往哪走

**标准库和现代 C++**

- `std::span`、`std::string_view`:不复制地引用一段数据。
- `std::optional`、`std::variant`:比异常更轻的"可能没有"和"多选一"。
- 范围库(C++20 的 `std::ranges`):`v | std::views::filter(...) | std::views::transform(...)` ,把第 19 课的算法串起来写,不产生中间容器。
- `std::filesystem`:路径和文件操作。
- `<chrono>`:时间。`<thread>`、`<mutex>`、`async`:多线程。

**算法的下一步**

- 更难的图算法:最小生成树(Kruskal 用并查集,第 37 课)、网络流、最近公共祖先。
- 字符串:Manacher、后缀数组、AC 自动机。
- 多维:线段树、树状数组、KD 树。
- 近似与随机化算法:数据流、采样。
- 大整数:用 GMP 这类库,不要自己写(第 43 课的累乘溢出就是例子)。

**工程能力**

- 测试框架:GoogleTest 或 Catch2(第 23 课)。
- 性能剖析:先用工具量,再优化。`perf`(Linux)、Visual Studio 的分析器。别凭猜优化。
- 读别人的代码:找一个小而成熟的 C++ 项目,读懂它的结构和取舍。
- 写点真东西:命令行工具、小游戏、配置解析器、简单的网络服务。

**两个建议**

1. **每门算法都要"能写出来"和"知道什么时候用"两个层次。** 工程里绝大多数时候是后者:用库,别自己写。但你必须知道库背后是什么、它的限制在哪(第 33 课的退化、第 36 课的负权、第 41 课的哈希复核)。
2. **对拍和实测,比推理可靠。** 这一课的案例、第 31 课的"哈希只快 2 倍"、第 37 课的"并查集比 DFS 快"、第 40 课的糖果,都是我或别人手推错了、跑一遍才发现的。养成"写完就跑、拿标准答案比"的习惯,比练心算更划算。

贯穿整门课的几条主线:

1. **内存:能不手动管,就不手动管。** `vector`、`string`、`unique_ptr` 覆盖绝大多数需求。
2. **左闭右开**这个约定,出现在数组、`vector`、算法、二分、归并、前缀和里。它让"长度 = 终点 − 起点",空范围无需特判。
3. **复杂度先估算。** n 多大,决定你能用什么算法。
4. **大 O 只是增长规律,不是倍数。** 常数和内存访问模式常常才是关键。
5. **不靠推理靠验证。** 边界要测,随机数据要和标准库或暴力版对拍。
6. **每个算法都要问"什么时候不该用它"。** 快速排序的退化、Dijkstra 的负权、贪心的反例、哈希的顺序 —— 知道边界,才不会用错。

## 小结

- 选型四步:估规模 → 明确要什么 → 看数据特点 → 先写对的再写快的,最后对拍和实测。
- 数据结构默认 `vector`;按键查值用 `unordered_map`;要顺序用 `map`;只取极值用堆;判断同组用并查集;前缀匹配用前缀树。
- 最大的坑集中在三处:**内存**(泄漏、越界、悬空、递归太深)、**标准库的误用**(`unique`、`accumulate`、对未排序数据二分、迭代器失效)、**算法细节**(二分差一、BFS 标记时机、0-1 背包方向、回溯不撤销、哈希不复核)。
- A* = Dijkstra + 不高估的启发式,结果同样正确,扩展的点数少得多。
- 手推会错,所以对拍和实测比推理可靠。
- 知道每个算法"什么时候不该用",比知道它怎么用更重要。
